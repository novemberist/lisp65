# 1.1-C EXT-relief design memo

Status: C1 owner-approved on 2026-07-15. The immutable decision input is bound
by `config/v11-c1-architecture-decision.json`; implementation remains subject
to the authorization gate below.

## Decision summary

Choose **compiler-tier deresidentization** for 1.1-C and retain direct Attic
execution as a post-1.1 architecture project.

The smaller cut recovers 9,573 resident code bytes while preserving the
current bytecode address model. That is far more than the 64-byte wave target
and keeps 1.1 focused on product polish. Direct Attic execution has a larger
19,228-byte ceiling, but it changes code addressing, L65M commit semantics,
reset recovery and every bytecode invocation path. Its gain is attractive; its
risk is not proportional to the immediate one-byte EXT emergency.

The single remaining byte is explicitly non-spendable. Source shelving alone
recovers zero EXT bytes because the VM still copies every loaded code object
into Bank 5 before execution.

## Option C1: deresidentize the compiler tier

### Proposed boundary

Build the three compiler sources as one SHA-bound L65M tier on the 1.1-A
shelf. Keep only the public entry seam resident. The admissible Bank-5
transaction is:

1. checkpoint the append-only code/directory/symbol/name-pool watermarks;
2. load the compiler tier from the verified Attic shelf;
3. compile into a detached output buffer, without installing the result;
4. prove that the buffered result has no compiler-private references;
5. retire the temporary tier and restore its watermarks;
6. install the buffered result only after the compiler tier is gone.

Installing the result before step 5 is structurally invalid: append-only user
code above the compiler tier would prevent a LIFO rollback. The current
compiler does install directly, so this cut depends either on the detached
buffer seam from 1.1-E or on a separately measured, non-EXT execution window
for the temporary tier. The latter is admissible only if the existing banked
code-address contract can use it without changing VM call paths; that must be
proved by a prototype rather than assumed here.

This is a purpose-specific transactional lifetime, not general `unload` by
another name. General LIFO unload remains 1.1-F. If the dependency proof or
watermark rollback cannot be made constructive, C1 stops rather than leaving
the compiler permanently loaded.

### Dependency cut that must be proved

- `eval`, `eval-buffer`, `compile-string`, `compile-buffer-to-lib` and
  `compile-file-to-lib` remain public entry seams.
- Compiler-private `%lcc-*` and `%fasl-*` functions do not escape in compiled
  code, literal graphs, macro objects or global value cells.
- Installed user functions reference runtime primitives, public functions and
  their own helpers only; no compiler-tier ordinal survives the transaction.
- Abort paths restore all five watermarks and the `*loaded-libs*` registry.
- 1.1-M may hold its output buffer across tier retirement, but it may not keep
  a pointer into compiler-tier code or metadata.

### Cost and risk

| Dimension | Assessment |
| --- | --- |
| Gross EXT recovery | **9,573 B** when the compiler tier is absent |
| Target coverage | 149.6× the 64-byte target |
| Bank-0 cost | expected small control seam, but **unpriced until a real link**; no debit is implied by this memo |
| Format impact | new shelf member/index row; existing L65M v2 remains valid |
| VM hot-path impact | none |
| Main implementation risk | detached-output/temporary-window seam, complete dependency proof and abort-safe watermark restoration |
| Evidence burden | compiler matrix, compile/install/execute after retirement, GC/OOM aborts, reset before first compiler load |

The important qualification is temporal: during compilation the tier consumes
its 9,573 bytes again. C1 creates durable idle/session margin and can finance
normal polish, but a Bank-5 implementation cannot precede the 1.1-E detached
buffer seam. 1.1-M must then prove that the temporary compiler load plus its
buffer fits the peak EXT budget. A peak failure is a design stop, not grounds
to lower the 16-KiB floor.

## Option C2: execute disk-library bytecode directly from Attic

### Required contract changes

The current directory stores an 8-bit bank plus a 16-bit offset, and
`vm_code_load` addresses the 24-bit Bank-5 space. Direct Attic execution needs
at least the following coordinated changes:

- an Attic-capable code address in every directory lookup and code-window DMA;
- enhanced-DMA handling in direct call, `funcall`, `apply`, closure and
  tail-call paths;
- a new rule for L65M literal patching, which currently mutates the staged
  Bank-5 blob during commit;
- reset-safe relocation: Attic survives reset, while symbol and object
  identities are reconstructed and cannot reuse stale patched literals;
- cross-container entry-ref and late-bound export behavior over the extended
  address space;
- new host VM, disassembler, diagnostic-map and all-engine differential
  representations of the address.

The reset point is decisive. Merely tagging an Attic address is insufficient:
today's committed code contains resolved runtime objects. Reusing those bytes
after reset would bind code to the previous session's object identities. A
sound design therefore needs either restaging/relocation on every reset or an
indirection format that keeps mutable resolutions outside the shelf.

### Cost and risk

| Dimension | Assessment |
| --- | --- |
| Gross EXT recovery | **19,228 B** for today's IDE+IDEX+M65D composition |
| Target coverage | 300.4× the 64-byte target |
| Bank-0 cost | inherently touches the VM hot path and enhanced-DMA state; **cannot be responsibly byte-priced without a prototype link** |
| Format impact | extended code-address and relocation contract; likely L65M evolution |
| VM hot-path impact | all bytecode calls and code-window refills |
| Main implementation risk | stale post-reset object bindings and cross-path address parity |
| Evidence burden | full four-engine matrix, designator parity, transaction matrix, reset/restage matrix and complete G5/G6 rerun |

This option is not rejected as a future architecture. It is rejected as the
first response to a 64-byte 1.1 relief target.

## Authorization gate for C1

Before implementation is promoted, a probe receipt must report all capacity
deltas and demonstrate:

1. an exact 9,573-byte resident exclusion before alignment effects;
2. a named explanation of every link-level deviation from that gross number;
3. at least 64 bytes of post-block EXT margin, with 16 bytes as the hard
   minimum for unfreezing later blocks;
4. zero compiler-private references after tier retirement and no installed
   output above the tier at rollback time;
5. identical compile/execute results before and after the cut;
6. fail-closed rollback for GC, OOM, malformed shelf data and reset.

Owner decision: **C1 approved for probe-first implementation**. C2 remains a
post-1.1 architecture project. This approval selects the cut; it does not
waive any item in the gate above.

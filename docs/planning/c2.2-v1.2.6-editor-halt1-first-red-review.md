# v1.2.6 Halt #1 — editor device First Red

Date: 2026-07-31
Candidate: Link 83, non-promotable
Disposition: **device discriminator attempted 2026-07-31; both authorized
contacts ended in attributable harness First Reds before the discriminator;
owner review required and Phase E stays closed.** No product classification,
fix, link, or third hardware contact is justified.

1. **Host replay of the exact transport.** Run the same
   one-key/one-visible-acknowledgement sequence on the host session
   runner past key 56. Host stall → mechanism is host-reproducible and
   the hunt is cheap. Host clean → bind the first state divergence
   (allocation counters, carrier indices, queue state) between host and
   the device captures at keys 50–56.
2. **New code first.** The Link-83 line-carrier reuse and coalescing
   are the newest moving parts: search their pools, indices and windows
   for any capacity or wrap constant at/near 55/56, and instrument the
   carrier-reuse path's state at the transition.
3. **The regression question, answered explicitly.** Run the same
   transport against the v1.2.5 editor image on the host: does the old
   renderer pass key 56? Old-stalls-too → Link 83 *exposed* a
   pre-existing bound (different release story, known-issue candidate);
   old-passes → Link 83 *introduced* it (pure regression, fix before
   any release). This distinction decides between fix-forward and
   re-park, so it is part of the attribution, not an afterthought.

## Host-attribution result

The exact loop now runs through the real C evaluator, VM and collector with
the product heap geometry. Its mocked typed queue presents one event, then one
empty `poll-key`, and does not release the next event until the cumulative
line is present in the host screen image. This is the same acknowledgement
boundary as the device run, rather than a bulk-input approximation.

Both images pass:

| Image | Key 55 | Key 56 | Key 57 | End |
|---|---:|---:|---:|---:|
| Link 83 | GC 23 | GC 23 | GC 24 | 80 keys, GC 39, OOM 0 |
| v1.2.5 source authority | GC 41 | GC 42 | GC 43 | 80 keys, GC 77, OOM 0 |

The Link-83 run also passes ASan/UBSan. A collection occurs while Link 83
processes key 56, but the host completes it and visibly acknowledges the key.
This is a useful correlation, **not** a hardware-GC attribution: the device
receipt did not capture `gc_runs` at the stall.

The two loop objects close the newest-code branch more sharply:
`%ide-drain-pending` has 31 identical opcode bytes in both generated images,
and `ide-run` has 71 identical opcode bytes. Their symbolic literal shapes are
also identical; only resolved directory ordinals move. `vm.c`, `interrupt.c`
and `c2_kernal_window.s` are byteidentical between the v1.2.5 authority and
Link 83. The only editor fill boundary is column 79; no capacity or wrap
constant exists at 55/56.

Therefore Link 83 has no host-visible 55/56 regression, and the old image also
passes on the host. This does **not** claim that v1.2.5 passes on hardware. The
first unresolved boundary is now physical `$D60A/$D619` delivery versus
target-only execution after consumption of key 56.

The bound receipt specifies one read-only, four-way device discriminator for
owner review: capture `$D60A`, `$D619`, `gc_runs` and PC immediately before
key 56 and at the stall. Queue-present, PC-inside-GC, and post-GC outcomes are
disjoint. The earlier idea of reading LA(17..20) is withdrawn: Link 83 was
built without `LISP65_HEARTBEAT`, so those stores do not exist in the ELF.

## Device discriminator — authorized 2026-07-31 (reviewer Class C)

The prepared read-only discriminator is authorized: **one physical
contact plus one reserve** only if the first ends undefined; cold-reset
rule and package-medium binding as standing; one-key/one-visible-ack
transport; reads limited to `$D60A`/`$D619`, `gc_runs` at `$B9F0`, and
PC — before key 56 and inside the hang. The LA(17–20) removal is
correct: those markers are not in the Link-83 ELF, and reading absent
markers would be the harness lying to itself.

Pre-registered disjoint interpretations, fixed before any number:

- **(a) key 56 never reaches the hardware queue** → the input/IRQ side
  owns the fault (the masked-source regime and keyboard path become the
  suspects); the renderer work is exonerated for the stall.
- **(b) key consumed, PC inside the collector, `gc_runs` advanced but
  the collection never completes** → a target-only GC hang in the editor
  state profile. This would be the second target-only GC anomaly beside
  the parked Link-77 OOM and re-opens that family with a live, repeatable
  specimen — the highest-information outcome.
- **(c) key consumed, collection completed, PC in the render/persist
  path** → the post-GC consumer owns the fault; the hunt moves to the
  redisplay/persist seam with a bounded PC address.

Whatever the outcome, it returns here as a prepared item; no fix, no
link, no further hardware beyond the authorized contact(s).

## Re-authorization after the setup losses — 2026-07-31 (reviewer)

Both contacts were consumed by setup errors before any measurement byte;
the rule-correct stop is acknowledged. This is the second session lost to
setup rather than measurement (the require discriminator lost its two to
transport), so the retry carries a structural rule, not just fresh budget:

**Standing rule, extending the cold-reset rule: every measurement row
begins with a machine-checked assert of its immediate context, not only
of the boot.** For this discriminator, binding preflight asserts before
key 1, in order: (1) cold reset; (2) the bound D81 AUTOBOOT banner
asserted by screenshot; (3) the editor state asserted as
`-- measure3 L1 -- 630/752` on screen. Any assert failure aborts the
contact immediately — a harness must never proceed past a failed
precondition into the measurement, because that is how a contact budget
turns into a setup lottery. The corrected runner already binds exactly
these gates; it is hereby the only authorized entry point.

**Authorized: one contact plus one reserve** under that corrected
runner. Reads, transport and the pre-registered (a)/(b)/(c)
interpretations are unchanged. Phase E stays closed.

## Disposition after six contacts, zero peeks — 2026-07-31 (reviewer)

**No seventh blind contact.** Six physical contacts have produced zero
discriminator reads; the stuck rule applies to sessions too. The
captures name two unguarded assumptions, and both just failed:

1. **The status line can lie.** The 626/630 resolution shows the editor
   status line rendering the *cached* status of a different editor. Our
   preflight asserts read the screen; against a caching status line they
   are unreliable. This is also a named product observation in its own
   right (status-line cache), booked for the next release review.
2. **Transport arrival was never proven.** Twice a virtual key hung
   unacknowledged (disc reserve; now scratch), and nothing shows whether
   it ever reached the hardware queue. An unproven transport makes every
   further hang unattributable by construction.

**Commissioned before any new contact (Class A, tool-side):**

- a **transport self-test**: after injecting a key, assert its arrival
  by reading the `$D60A`/`$D619` queue directly — editor-independent;
  this assert becomes part of every keystroke the runner sends;
- preflight state asserts move from the status line to a **buffer peek**
  (the fill value read from memory, not from the cached render);
- the runner treats **any hang as a measurement event**: the
  queue/gc_runs/PC peeks execute at whatever position a hang occurs —
  a hang is never again classified as setup and skipped past unread.

**Conditional authorization, no further owner round needed:** once the
corrected runner demonstrates these three properties in a host dry-run,
**one contact plus one reserve** is authorized under the standing
cold-reset and context-assert rules. With arrival proven and
peek-on-any-hang in place, every possible outcome of that contact is
informative: transport red = tooling, attributable; hang with proven
arrival = the product, peeked at last.

## Observed-transport outcome — contact plus reserve

The two conditionally authorized contacts are consumed.  Neither permits a
product claim:

1. Contact 1 proved that stopping the CPU *before* virtual-matrix injection
   prevents the key from reaching `$D60A/$D619`; the runner stopped at its
   transport guard before executing product setup.
2. Contact 2 replaced that ordering with a hardware breakpoint at `$E01C`,
   the linked `lda $d619` in `c2_kernal_event_poll`.  The injected `(` reached
   the product consumer.  The capture has `PC=$E01F`, `A=$28`, last opcode
   `AD 19 D6`, and next instruction `sta $d619`; `$28` is the exact expected
   PETSCII byte.  The runner nevertheless rejected the key because it modeled
   the breakpoint as pre-instruction and expected `PC=$E01C` plus a still-live
   queue-present bit.  On this core the breakpoint report is post-instruction;
   the queue registers read zero after the `D619` load.

Thus contact 2 contains a proven arrival and an attributable **tooling
First Red**, not a product failure.  It stopped at the first character of the
first setup form, so no editor hang occurred and no queue/GC/PC discriminator
peek was due.  Outcomes (a), (b), and (c) remain unmeasured.  The
contact-plus-reserve budget is exhausted; no product fix, link, or further
hardware contact follows without owner review.

**Authorized: one contact plus one reserve, under a minimal-change

If this pair also ends without a discriminator read, the next step is

## Outcome

The renderer-allocation change is host-correct and the first forty
device keys stay below the pre-registered collection envelope, but it
does **not** close the owner's usability report.  With the transport
reduced to one key followed by one visible acknowledgement, the editor
accepted and displayed 55 `a` characters.  The 56th `a` did not appear
during 120 seconds.  The screen remained stable, the fail-closed red
frame did not fire, and RUN/STOP returned to a live REPL.

This excludes the earlier bulk-submission explanation.  It does not yet
attribute the product mechanism behind the 55-to-56 transition.

## Harness findings kept separate

The session found and corrected three harness-only mistakes without
changing product bytes:

1. multi-key virtual submissions did not establish product queue
   capacity, so the authoritative run used one key per visible
   acknowledgement;
2. the original D2 fixture called the non-exported `list->string` from
   the REPL; the replacement used public `string-append` and
   `substring`;
3. `(time)` renders its frame count and result on one row (`74 t`,
   `80 t`, `0 3`); the checker now binds the result after the matching
   form instead of assuming a separate result row.

None of these changes explains or removes the D1 stall.

## Decision boundary

No product fix, second link, or device retry is authorized at this
halt.  The narrow next choices are:

1. **Attribute the deterministic transition host-first (recommended):**
   reproduce or model the state after 55 accepted keys, identify the
   first non-returning renderer/input phase, and return with a named
   mechanism before changing product bytes.
2. **Re-park v1.2.6:** retain Link 83 and this receipt as non-promotable
   evidence, restore the working source to the released v1.2.5
   authority, and move to the next commissioned direction.

Publishing Link 83 is not a valid option: the release's defining device
criterion is red.

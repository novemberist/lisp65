# C2.2 cross-invariant matrix

Status: **commissioned by owner/reviewer 2026-07-21; to be filled by Codex
against existing contracts and receipts — no new code, no new link**

Date: 2026-07-21
Reviewer: Claude (architecture review); owner approval: Alex

## Purpose

The nested-eval finding (link 32) had a recognizable shape: two subsystems,
each individually proven, whose *crossing* no contract had considered.
The same shape produced the profile-switch gap and the dual-formula BCODE
encoding. This matrix walks the remaining crossings systematically instead
of waiting for hardware to serve them one at a time.

This is a paper exercise. Each row is answered from existing contracts,
receipts and code — by citation, not by intuition. Filling a row spends no
capacity and changes no product byte.

## Method

Each row gets exactly one status:

- **PROVEN** — a receipt or passed gate covers the crossing directly.
  Cite the receipt/gate.
- **EXCLUDED** — a contract makes the crossing structurally impossible
  (not merely unlikely or "code doesn't do that today"). Cite the contract
  clause. "The current code happens not to" is NOT exclusion; that is OPEN.
- **OPEN** — neither. Every OPEN row gets a disposition:
  - `fixture` — needs a negative/positive test against existing behavior;
  - `addendum` — needs a contract decision before C2.2 acceptance;
  - `benign` — needs a written argument why the crossing cannot matter
    (the argument itself is then review material, and the row stays listed).

Honesty rules: prefer OPEN over a stretched EXCLUDED. A row answered
"probably fine" is OPEN/benign with the argument written out. Rows may be
added by Codex; rows may not be removed.

Completion gate: the C2.2 acceptance chain does not start while any OPEN
row lacks a reviewed disposition. (Dispositions may schedule work into
C2.3 where the affected surface is itself C2.3 — e.g. restart-repl — but
the scheduling decision must be explicit.)

## The matrix

### A. GC crossings

| # | Crossing | Question |
|---|---|---|
| A1 | GC × open overlay transaction | Can a natural (allocation-triggered) GC run while an append transaction is open? If yes: are half-staged records invisible to the root scan, and does the transaction survive the collection? If no: what structurally prevents allocation inside the staging path? |
| A2 | GC × transient high-edge | The transient wrapper edge is new root surface. Is its scan bound into the B2 single-source root area, block-read (32-byte pattern), and does watermark reset happen atomically with respect to a GC that could run mid-abort? |
| A3 | GC × hot code window / refill | Does the GC ever read or move anything the refill path caches (window contents, directory hot state)? Non-moving GC is a load-bearing invariant — cite where the code-window state is declared outside the collected set. |
| A4 | GC × C2D publication (steps 5–7) | Publication journals prior state, then publishes directory range, then export cells. Can a GC interleave between these steps, and if so, does the root scan see a consistent directory at every interleaving point? |

### B. Non-local exits

| # | Crossing | Question |
|---|---|---|
| B1 | longjmp × open transaction | Contracted by the nested-append-unwind addendum (48-case probe). Row exists to bind the *product* proof once implemented: BUSY/error abort mid-transaction leaves C2D counters byte-identical. |
| B2 | RUN/STOP break × open transaction | A user break is a longjmp-class exit and can arrive at any poll point. Is the break path anchored to the same Bank-5 unwind journal as error exits, or can a break skip rollback the way the link-32 longjmp did? |
| B3 | RUN/STOP break × DMA transport in flight | Can the break fire between DMA-list setup and completion check inside a refill or staging transport? What state does the poll path see? |
| B4 | longjmp × island installer | Can any exit path fire inside the INSTALLING state (guard active, island half-written)? If the installer is provably poll-free and error-free, cite the closure receipt; otherwise OPEN. |
| B5 | Error inside publish-last seam | The 34 named post-link mutable bytes (32-B verifier table + 2-B CRC seam) are written after the link; at runtime the C2D header commit marker is written last. Can an error between journal write and header commit leave a torn marker, and is a torn marker fail-closed on next read? |

### C. Freezer and persistence

| # | Crossing | Question |
|---|---|---|
| C1 | Freezer × open transaction | Freeze can happen at any frame boundary. After thaw, is an open transaction's state (Bank-5 journal, staged-but-unpublished records) fully consistent, and was this ever exercised, or only freezer-during-idle? |
| C2 | Freezer × $E000 window (full product) | The byte-identical-after-freezer proof predates the full-profile product and the current window contents. Does an equivalent hardware receipt exist for the link-32-era window, or does the old receipt get inherited across a product identity change (which the no-inherited-green rule forbids)? |
| C3 | Freezer × handoff state machine | Freeze during a KERNAL↔owned transition (any non-steady state of the handoff machine). Excluded by construction (transition runs with interrupts/freezer entry impossible)? Cite; else OPEN. |
| C4 | Cold reset × partially published C2D | Reset can interrupt any DMA write to Bank 5 / Attic staging. Is every persistent structure covered by a commit-marker-last discipline such that a torn write is detected (not interpreted) on the next cold boot? |
| C5 | Attic tenant staleness × session directory | Stale-generation rejection exists in the negative matrix (restage → new session). Does it also cover the asymmetric case: attic content *newer* than the directory expects (e.g. interrupted re-stage that completed the attic side but not the directory side)? |

### D. Interrupts and input ownership

| # | Crossing | Question |
|---|---|---|
| D1 | Owned IRQ × publication window | Can the owned IRQ (queue/frame source) observe or touch any structure that publication steps 5–7 mutate? If the IRQ only touches the typed queue and frame counter, cite the IRQ closure; else OPEN. |
| D2 | Owned IRQ × island install / handoff | Is the IRQ installed before, during, or after island installation, and is the ordering contracted (not incidental)? The link-31 lesson — infrastructure used before installed — applies to the IRQ vector itself. |
| D3 | Typed queue overflow × break delivery | If the queue is full at the moment RUN/STOP is pressed, is break delivery still guaranteed (the gapless-break condition of the KERNAL-unmap commission), and is there a fixture? |

### E. Generation and lifecycle

| # | Crossing | Question |
|---|---|---|
| E1 | Generation change × hot cache | Restage increments the generation; refills are generation-keyed by contract. Is the *hot cache* (persistent hot state introduced by the hot-refill cut) also invalidated on generation change, or does it hold pre-restage bytes that the generation key never re-checks? |
| E2 | Generation wrap (u16) × fail-closed path | Wrap requires cold boot by contract. Fixture exists? (Forcing a wrap in test may need a host-side harness; a proof by construction with cited code is acceptable for EXCLUDED.) |
| E3 | restart-repl (C2.3) × transient high-edge | Restart clears heap/directory/resolutions/exports. The transient edge and its watermark are new members of that list. Row exists so the C2.3 design inherits it explicitly. Disposition `addendum` scheduled into C2.3 is acceptable. |
| E4 | restart-repl (C2.3) × open transaction | A restart request arriving while a transaction is open: refused (BUSY-like), or does it force-abort through the unwind journal? Either is designable; undecided is OPEN/addendum for C2.3. |
| E5 | Bounded nesting (4) × user-visible error | When depth 5 is refused: does the user get a defined Lisp error (catchable, message contracted in L65E), or a VM fault? Cross-links the nesting contract with the error-surface contract. |

### F. Capacity and growth at runtime

| # | Crossing | Question |
|---|---|---|
| F1 | C2D growth × Bank-5 ceiling | Session appends grow the directory (observed: 6/588/2264/283 → 9/591/2278/285). Is there a checked ceiling with a defined refusal (graceful error) before Bank-5 exhaustion, or is the first overflow undefined behavior? |
| F2 | Transient edge growth × collision with persistent edge | The two edges grow toward each other. Is the meet detected at reservation time with a defined error, and is there a fixture at exactly ±1 record? |
| F3 | Name pool / symbol growth × session appends | Appending definitions consumes symbols (320) and name-pool bytes (4,897). Are both exhaustions defined errors at the append seam, consistent with the F1 refusal? |

## Deliverable

Codex returns the matrix with every row statused and cited, as one receipt
(JSON mirror welcome), plus the list of OPEN rows with proposed
dispositions. Review then decides dispositions row by row. No fixture or
addendum work starts before that review — the matrix is intelligence,
not a work order.

## C1 terminal disposition — 2026-07-26

The owner-approved bundled Link-66 hardware appointment reached a new error
class before Cutpoint 3: the non-promotable carrier's definition returned
`bad bytecode` before any Freezer action. Under the pre-authorized terminal
rule in the v1.2 scope memo, this does not start another C1 diagnostic cycle.

C1 is therefore **documented/C2.3-deferred, not PROVEN**:

- Cutpoints 1 (`journal-written`) and 2 (`staged-before-header`) remain accepted
  hardware results.
- Idle Freezer identity remains a permanent per-product row. Link 66 passed it
  with complete Bank-2/Bank-3 identity, `$e000` identity except for the three
  contracted live cells, family/generation `(1 4)`, and post-return arithmetic.
- Freezer entry during a persistent definition or append transaction is a
  documented C2.2 product restriction and a mandatory C2.3 lifecycle
  obligation. It is not silently treated as safe.
- The C2.2 matrix gate may fall with this reviewed disposition. No receipt may
  relabel C1 as PROVEN, and C2.3 acceptance remains blocked until it supplies a
  reviewed rule and hardware fixture for this crossing.

This terminal disposition changes no product byte. It replaces the earlier
C2.2-before-acceptance closure schedule for C1; it does not alter any other
matrix row or lend hardware evidence across product identities.

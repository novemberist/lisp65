## v1.8 substrate D-session protocol correction — 2026-08-28

The first substrate-neutrality row incorrectly asked for Cursor Left while
editing the raw native `lisp65>` input line.  The owner's correction exposed

`(read-line)` first and exercised Cursor Left inside that Bank-2 editor.  It
never claimed Cursor Left/Right editing in the native C line collector.

not an early submission and not a v1.8 regression.  The mechanism is exact:
Cursor Left arrives as PETSCII `$9D`; the unchanged native collector rejects
unhandled controls through `(c & $7F) < $20`, so `$9D` becomes `$1D` and
enters the standing visible reader-error path.  `src/repl.c` is byte-for-byte

release-terminal substrate world deliberately loads no optional library.

only the native collector's supported ordinary-input and Delete behavior.

## Native-prompt cursor attribution — three-way question closed — 2026-08-28

The session fact `loaded_library_roles: []` identifies the observed world, but
does not by itself decide whether a boot-time `v16core` load could rewire the
prompt.  The host attribution therefore ran the question at the machine-code
boundary over three real ELFs: the sealed v1.7 release (`e8ca0734...`), the
delivered v1.8 substrate candidate (`67f89b73...`), and the historical Block-3
candidate (`a5c5af37...`).

All three `repl` functions have the same ownership topology.  The startup
banner executes through one direct `vm_run_dir` call and returns to a fixed
resident loop.  That loop owns an inline C collector, calls
`lisp_input_event` directly exactly once, and has zero `__call_indir` editor
calls.  Neither a boot-time nor a mid-session `require` can replace this
collector; `v16core` changes the Lisp binding used by explicit `(read-line)`
forms only.

The exact post-event machine path was replayed from each ELF.  In the sealed
v1.7 release, Cursor Left `$9D` passes the control comparisons, takes the
linked rejection branch, loads stable error code 5, and calls
`lisp_abort_code` before Return, parsing, or evaluation.  v1.8 and Block 3 do
the same.  The visible words `reader: invalid token` come from the shared error
catalog, but the linked producer is the native C collector; the partial line
was not evaluated.

This also corrects the historical evidence boundary.  The v1.6 cursor session
entered explicit `(read-line)` after requiring `v16core`.  The v1.7 release
D-session had no cursor row.  The Block-3 line-editor row did not specify an
explicit `(read-line)` entry, while its real ELF still used the resident C
collector at `lisp65>`; it therefore never proved native-prompt navigation.
The observed v1.8 event is **never-supported native-prompt behavior, not a
v1.8 regression**, and the live `nthcdr` repair is unreachable from it.

The maintained Known Issue carries both honest workarounds: direct native
input uses Delete plus suffix re-entry; programs that call `(read-line)` may
make `v16core` boot-visible and require it from `INIT.L65`.  The latter enables
the explicit Lisp editor, not Cursor movement in the C prompt itself.

The v1.9 register now carries the product-policy choice explicitly: known
navigation controls become harmless no-ops in the minimal collector, or the
prompt is routed through/default-loads the Bank-2 editor under a full price.
Future release D-sessions split the **bare boot with zero optional roles** into
its own row group before any library-loaded surface is tested.  A green
`(read-line)` row may never again stand in for a bare-prompt claim.

The attribution used zero WPLTOs, links, media builds, and device contacts.
It removes this finding as a Ship blocker but does not itself infer an owner
`Ship` word.

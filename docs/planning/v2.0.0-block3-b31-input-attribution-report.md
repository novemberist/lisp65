# v2.0 Block 3 B3-1 input attribution

Status: **complete — host-only; no repair, link, medium or device contact**.

## Named mechanism

The repaired Block-3 world arms the resident input ring at `read-line` entry,
then its new idle scheduler `%rl-poll` asks `key-event` in mode 0. Those two
facts do not compose on the target. While the ring is armed, the raster IRQ is
the sole owner of the physical keyboard queue: it acknowledges each event and
moves it to the private ring. Mode 0 reads the public queue, which is empty by
the time `%rl-poll` looks. The first key remains stored in the ring, no editor
dispatch occurs, and the visible prompt therefore appears frozen.

This is the **armed-ring/public-queue source split**. The blink-idle rewrite is
the carrier because it introduced `%rl-poll`, but the mechanism is input
ownership, not scanner/blink service time.

## Final-world proof

The frozen repaired pair is ELF `75f57003…`, PRG `89963ac6…`. Its resolved
profile contains both input-capture and hybrid consumption. Its emitted
`%rl-poll` object is 197 bytes and contains `PUSHI8 0; CALLPRIM key-event` at
bytecode offsets `$002C/$002E`. Its emitted `read-line` object is 118 bytes and
materializes the `$FF8D := $00` arm owner.

The target implementation separates the modes explicitly: modes 0/1 call the
public queue reader; modes 2/3 call `c2_kernal_input_take`, the only path that
increments `C2K_INPUT_EVENTS_TAKEN`. A one-event ownership execution therefore
ends as follows:

| World | raw | seen | stored | taken | editor result |
|---|---:|---:|---:|---:|---|
| Block-3 mode 0 | 1 | 1 | 1 | 0 | `nil`; event remains in ring |
| counter-mutation mode 2 | 1 | 1 | 1 | 1 | normalized `a`; ring empty |

The accepted v1.9 editor used precisely the private route: its idle read was
`%rl-render(row=-1)`, which calls `key-event 2`. Its hardware row accepted
cursor motion, insertion and evaluation.

## Why the host was green

The Block-3 framebuffer fixture rendered `lisp65> abc`, but its mode-0
`key-event` consumes the fixture's `key_events` list directly. It does not run
the asynchronous target ordering in which the IRQ first transfers that entry
to the private ring. Raw capture exists in the executor only at an explicit
peek seam. The host therefore proved the editor over a queue state that cannot
exist on the armed target.

This is a fixture-fidelity gap alongside the product wiring defect. A living
interactive claim must execute the delivered consumer under the delivered
ownership/arbitration model; arming and consuming are one end-to-end property.

## Disposition

No repair is made here. The result feeds the commissioned interactive
delivery-chain block, whose deliverable is a known-good interactive world that
survives packing, composition and boot. v2.0 remains reshaped around pillars 2
and 3.

# 2.3 Product Authority Rebind — work plan

**Commissioned:** 2026-08-18 (owner: "Einverstanden" to the 2.2 block
recommendation)
**Position:** runs after the 2.2 housekeeping block and **before** anything
from the v1.6 agenda. v1.6 does not open on a tree whose product authorities
predate its own sources.
**Form:** host-only, zero device contacts. One owner touchpoint at the end.

## Why this card exists

The 2.2 block established, with receipts, that ten `check-source` gates bind
product authorities that predate the library and C sources shipped in
v1.5.0 (`src/mem.c`, `src/c2_platform_dma.c`, `src/c2_product_runtime.c`,
the linker driver). The emitter is deterministic — two consecutive emissions
agree byte for byte — so this is staleness of the bindings, not
nondeterminism, and it cannot be repaired by any amount of housekeeping. It
needs a product link cycle, which is a product act.

Report: `docs/planning/2.2-housekeeping-block-report.md`.

## Order of work

### Step 1 — unwedge the everyday product target (prerequisite)

`make workbench-product` cannot run at all: the target routes through the
frozen v1.5 public driver, and with the selected manifest absent it chooses
`build`, which refuses because its one-shot guard tests `BUILD.exists()` — a
directory the same tool's own `ide-check` preflight already created.

The guard must keep its meaning: **the v1.5 public build happens exactly
once.** Repair it by testing what the build itself owns rather than a parent
directory a sibling action also populates, or by routing the everyday target
back to the canonical product builder and leaving the frozen public driver on
the release path. Either way the one-shot property is proved by mutation: a
second public build attempt against a completed public build stays refused.

### Step 2 — rebind the product authorities

Run the product link cycle so the emitted artifacts and the bound authorities
describe the same world, and the (source, bound artifact) pair matches again.
No product behavior changes in this card: the link is a rebind, and any
byte-level product difference is attributed before it is accepted, not after.

### Step 3 — prove the tail

`make -k check-source` runs to completion with **zero** failures and an empty
exception list — the bar the 2.2 block could not reach. `-k` is required: a
stopping run is what hid this tail in the first place.

### Step 4 — fix the idempotence defect

`check-source` currently verifies bound artifacts in an early gate that a
later target in the same run re-emits, so a green run leaves the tree red for
the next one. Separable from steps 1-3 and may land in any order relative to
them, but it must land in this card: the bar in step 3 is not trustworthy
while a green run un-greens itself.

Proof: two consecutive full runs, the second green without any intervening
repair.

## Out of scope

New product behavior, new freight, and anything from the v1.6 agenda. A
finding that wants a feature becomes a parked row.

## Exit

Owner touchpoint: the card report, carrying the two consecutive green runs,
the rebound authority set, and the mutation that keeps the public build
one-shot. Owner release of that report opens the v1.6 commission.


## Card released — 2026-08-18 (reviewer)

All four steps are met and independently verified. The one gap the reviewer
found -- the closing commit's own report was unclassified, which reddened the
document index -- was repaired, and a confirming `make -k check-source` on the
tree including that commit ran green (exit 0, zero failures, clean worktree).

The card is closed. The v1.6 commission is open.

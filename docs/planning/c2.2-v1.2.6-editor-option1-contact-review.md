## What the contact measured

The device cold-booted the bound product medium and entered the scratch editor.
The runner submitted the historical 34-character scratch line by ordinary
input, without any per-key breakpoint. The live `ide-buffers` reader then
observed a stable fill of 13 for the full 120-second bound instead of 34.

The single authorized halt produced all four witnesses:

| Witness | Before input | At stop |
|---|---:|---:|
| `$D60A` queue state | 0 | 0 |
| `$D619` queue byte | 0 | 0 |
| `gc_runs` | 0 | 1 |
| PC | running | `$E000`, `c2_kernal_event_poll+0` |

The mechanical classifier selected its broad c predicate because a collection
completed and the stopped PC was outside `gc_collect`. The stronger reading is
more limited: `$E000` is the idle event poll, not the render/persist path. The
collector returned, the queue was empty, and only 13 of 34 submitted setup
characters persisted. Thus the contact did **not** reproduce the original
key-56 editor stall and did not expose a live target-only GC hang. It exposed a
normal-input setup loss before the historical state existed.

This does not reopen the single-key arrival question closed by contacts 8–10.
It proves only that a multi-character normal-input submission cannot be treated
as lossless without an acknowledgement boundary. The CPU was resumed after the
receipt; no breakpoint existed and no product byte changed.

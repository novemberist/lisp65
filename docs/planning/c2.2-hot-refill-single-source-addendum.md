# C2.2 hot-refill single-source addendum

## Trust boundary

The C2 stage/decode path validates the catalog and image identities, entry and
literal ranges, every descriptor kind, direct resolution, canonical root
ordinal and published root value before the generation becomes callable. The
published shelf bytes are immutable, and a session append becomes visible only
through its atomic header/publication transition. A restage invalidates the old
generation before another boot family can publish.

Therefore the hot refill path does not need, and must not carry, a second copy
of the content validator. It can consume only data reached through
`c2_entry_records`, which requires the active product context, a finished
phase-13 state and the current directory generation. The hot path retains the
bounds required for safe addressing and fails closed on a later descriptor,
resolution or root transport error. Those transport failures are not a second
content-validation domain.

This is a stronger boundary than validating repeatedly: manipulated content
must be unable to reach the hot path at all. The permanent stage negatives
cover invalid descriptor kinds, invalid direct entry resolutions, out-of-range
root ordinals and non-pointer roots. The hot fixture separately forces the two
possible post-publication transport failures.

## One materializer

`c2_stream_product_materialize_entry` is the only product entry materializer.
It accepts the active decoder context, one directory ordinal and the bounded
hot-value destination. It obtains all directory, image, metadata and entry
records through `c2_entry_records`, then resolves the already validated values
through the lean child seam.

Both consumers call this same function:

- the VM refill in `c2_product_entry_read`;
- the retained phase-13 ABI entry in `c2_stream_phase_13`.

No second materializer, private record walker or phase-13 descriptor
interpreter may enter the product closure. A source gate and linked control-flow
check enforce this rule.

## Claim limit

The authorized work is a semantic/source proof followed by exactly one
product-shaped Resident-Island capacity and placement seed. It makes no boot,
hardware, latency, promotion or performance claim and authorizes no product
link. Link 29 remains untouched. Any red capacity or structure gate stops the
attempt before a product link.

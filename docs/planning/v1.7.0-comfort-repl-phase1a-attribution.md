# v1.7 Comfort REPL Phase 1a attribution

Status: **mechanism named; Phase 1a complete; Phase 1b awaits its owner
touchpoint**

## Result

The sealed `(repl)` failure is a **library-to-product profile-capability
closure gap**. `%repl-step` contains this target bytecode at logical PC
`$004C`:

```text
CALLPRIM 12:screen-write-string argc=3
```

The selected product enables `LISP65_VM_SCREEN_PRIMS` but does not enable
`LISP65_SCREEN_WRITE_STRING`. ElfTruth over the sealed final ELF resolves
CALLPRIM table entry 12 to the same tombstone used by primitive IDs 1 and 2.
The emitted sink is `LDX #2` followed by the shared `vm_status` store; ordinal
2 is `VM_BADOPCODE`. The target therefore never enters the screen writer. It
does exactly what the user saw: `*** vm: bad bytecode`.

This also explains the host/target split. `bytecode_p0.py` implements primitive
12 unconditionally as a dialect-wide facility, while the linked target is a
profile-selected subset. The host gates proved the semantics of a primitive
that the selected product did not deliver.

## Why the prior seam hypotheses were plausible but wrong

The failure happened immediately after `%rl-screen-tail` returned across a
streamed code-window boundary, so refill and operand lifetime were reasonable
first candidates. They are now excluded:

- the sealed live capture contains the correct caller window;
- fresh target reductions showed streamed Lisp return, immediate `DROP`, NIL
  and fixnum results, and unary CALLPRIM all completing correctly;
- the operand-root ordering repair reproduced the same device failure; and
- the final dispatch table proves that execution is rejected before
  `screen-write-string` can touch the framebuffer.

The minimal target reduction that separated the cases was therefore reporting
the capability boundary, not an argument-count or screen-memory defect:
`numberp` after refill works; `screen-write-string` after refill reaches its
profile tombstone.

## Existing contract, missing closure

This capability was not undocumented. The standing surface-delivery contract
already says that CALLPRIM 12 requires `LISP65_SCREEN_WRITE_STRING` and that
the canonical Workbench otherwise carries `screen-bulk-p` as its resident
fallback. The blind spot was downstream: no gate joined a library's emitted
native-primitive consumers to the capabilities of the final product selected
to load it.

Phase 1b must add that closure:

> Every native primitive consumed by a library is delivered by the selected
> final product profile.

The gate must derive both sides — consumed CALLPRIM IDs from the emitted
library objects and delivered sinks from the final ELF/profile — so a registry
entry or a dialect-wide host implementation cannot stand in for delivery.

## Boundary and next decision

Phase 1a changes no product source, runs no WPLTO or link, builds no medium and
uses no device contact. It names the mechanism within the three-day box, so
the automatic Block-3 pivot does not fire.

The commissioned next step is the owner touchpoint for Phase 1b. That decision
may price either delivery of `LISP65_SCREEN_WRITE_STRING` in the product or a
Comfort implementation that consumes the already delivered fallback. This
attribution authorizes neither choice.

# C2.2 overlay transaction-authentication addendum

Status: **one host proof and one product-shaped capacity/placement seed authorized**

Date: 2026-07-20

## Evidence belongs to its invariant

Link 30 proved that the direct hot materializer works, but both the first and
second call still cost 131 frames. A top-level form crosses 27 runtime-overlay
slices. Each crossing repeated the unchanged family header, build identity and
complete directory CRC, producing at least 329,769 CRC/wipe byte visits per
form.

The catalog proof is now scoped to the append transaction whose slices consume
it. The first slice authenticates the selected session family, nonzero
generation, catalog header, profile identity, directory geometry and directory
CRC. Later slices in that same transaction reuse only those catalog outputs.
They still authenticate their own record, payload CRC, bounds and entry point,
and still wipe and verify the shared target after use.

This does not weaken validation: within a session generation the family image
is immutable and identity-bound, so repeating its catalog proof between two
slices adds no information. Trust is discarded at transaction end, on any
error or abort, and before any family/generation transition. The first slice of
the next transaction therefore performs the full catalog proof again.

## Permanent edges

The host mutation matrix proves both boundaries that amortization could
otherwise obscure:

- changing a payload between two transactions in the same generation is still
  rejected by the per-slice payload CRC before execution;
- changing catalog/profile identity across a generation transition requires
  and fails fresh catalog authentication.

An attempted family transition while a transaction is active is itself a
fail-closed error. The positive fixture also counts one catalog verifier call
for two slices while observing two record and two payload executions.

## Integration and claim limit

The optimized boundary surrounds the complete product `c2_product_install`
operation: emitter, append, transient execution and rollback. The standalone
staged-append entry gets its own bounded transaction. The low-level emitter
control surface remains semantically valid but is outside this performance
claim; its separately invoked operations retain the ordinary full-auth path.

The authorized work changes no product SHA and creates no product candidate.
Host/source/mutation gates run first, followed by at most one product-shaped
capacity and placement seed. Bank-0 BSS starts with only 19 bytes of headroom,
and the owned $e000 window is closed to new tenants: `$e000 delta = 0` is a hard
gate. Any red result stops before a product link.

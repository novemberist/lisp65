## 2. Why another patch cycle is rejected

The failure boundary currently collapses all `VM_BADOPCODE` origins to a
status code and discards the already-live execution coordinate.  Post-link
holds can preserve one guessed edge at a time, but no single hardware-stable
cell owns the logical PC across nested VM and install unwinds.  Three cycles
have now demonstrated that this is a product observability gap, not a missing
fourth patch site.

The next mechanism must be an ordinary product error contract.  It must travel
through normal control flow, survive nested propagation, and remain useful to
users after this incident.

## 3. Proposed contract: BADOPCODE status plus typed detail

Extend the existing status-plus-detail precedent without adding a latch:

- `vm_status` remains the status channel.
- The existing ordinary `obj` return remains the detail channel.
- `vm_check_status` remains the sole terminal consumer; the innermost non-OK
  detail wins and outer frames may enrich only `NIL`.
- No new global, BSS byte, GC root, journal field, or error string is allowed.
- `VM_DIRMISS` retains its closed `SYMI | BCODE | NIL` detail union unchanged.
- `VM_BADOPCODE` gains the disjoint `FIXNUM | NIL` union.  The fixnum is a
  diagnostic coordinate, never a symbol and never a forged BCODE:
  nonnegative values are logical bytecode PCs; a small, contract-enumerated
  negative range identifies pre-execution install boundaries for which no PC
  exists.
- The existing L65E renderer already transports a detail object.  Its target
  leaf gains one BADOPCODE/FIXNUM rendering case; every foreign detail domain
  remains fail-closed.

This avoids the semantic lie of encoding a PC or phase ID as a 12-bit directory
handle.  It also makes the product permanently capable of reporting the exact
class of internal invariant failure that currently costs hardware patch cycles.

## 4. Required proof surface

The contract/probe must include:

1. all raw `vm_run_inner` BADOPCODE exits classified as `PC available` or
   `pre-PC`; no producer may invent a coordinate;
2. every `c2_product_install` failure boundary assigned one negative typed
   stage value, including transaction begin/end, emitter, append, transient
   execution, rollback, and cleanup;
3. nested propagation proving that an outer BADOPCODE cannot replace an inner
   non-`NIL` detail;
4. terminal mutations for lost detail, overwritten detail, forged BCODE,
   forbidden SYMI, out-of-range FIXNUM, and success carrying stale detail;
5. an end-to-end zero-literal path: emission, append, publication,
   installation, call, and an injected failing opcode whose rendered coordinate
   matches the oracle;
6. the existing `%c2h` success fixture and all current DIRMISS detail fixtures
   unchanged.

## 5. Capacity and stop rules

Link 50's bound walls are:

| Currency | Headroom | Contractual usable remainder |
|---|---:|---:|
| Bank-0 text | 37 B | 5 B above the 32-B LTO-noise reserve |
| Ordinary BSS | 213 B | no new state is permitted anyway |
| Fixed hot block | 33 B | available only by explicit placement |
| Resident island | 5 B | effectively closed |
| E000 | 58 B | 4 B above the terminal 54-B floor |
| Session aggregate | 98 B | hard 64-KiB ceiling |

Therefore no source-size estimate authorizes implementation.  One
product-shaped WPLTO probe is the only capacity truth.  It must preserve text
headroom at least 32 B, E000 at least 54 B, and the Session aggregate at most
65,536 B.  Touching either protected reserve triggers the already contracted
scope triage; it does not reopen a floor or anchor negotiation.

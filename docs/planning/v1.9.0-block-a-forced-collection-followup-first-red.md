# v1.9.0 Block A — forced-collection follow-up First Red

Date: 2026-08-30

Status: **FIRST RED — DELIVERED CLIENT ARMS CAPTURE BUT DOES NOT CONSUME IT**

The owner completed the bound short-line choreography and the machine printed
the numeric oracle `7`.  The single authorized stop then read
`$BCFC..$BCFF` as:

```text
raw  seen  stored  taken
02   02    02      00
```

No explicit resume command was issued.  After the monitor command exited, the
owner nevertheless observed the evaluation finish as `(7 nil)` and the live
`lisp65>` prompt return with its active cursor.  The monitor therefore did not
leave the CPU durably stopped; this corrects the initial postcondition without
changing the four bytes captured while the wait was active.  The visible
oracle and later normal return prove the short stimulus completed, and the
bound 199 printable insertions cross the 192-cell nursery.  The counter wall is
nevertheless red: two events reached the IRQ producer and ring, while no event
was removed through the ring consumer.

## Mechanism

The final r7 `read-line` does close, zero and arm Capture.  It then constructs
exactly this eight-cell editor state:

```lisp
(list head head head 0 0 0 columns row)
```

The delivered `%read-line-loop` chooses its input route with:

```lisp
(if (nthcdr 8 state)
    (%rl-render nil 0 0 0 0 -1)
    (key-event 1))
```

`nthcdr 8` of the delivered eight-cell state is NIL.  The real client
therefore enters public blocking `key-event 1`, whose final native route calls
`lisp_input_event()` and reads the hardware queue.  It never enters private
mode 2 and therefore never calls `c2_kernal_input_take`.  Meanwhile the armed
raster IRQ remains a second reader and can remove events into the ring.  The
device bytes are the direct signature of that split ownership: producer
progress through `stored`, zero consumer progress at `taken`.

The earlier host wall exercised the Hybrid fixture in a state shape that made
the private route reachable.  The armed-lifecycle gate proved only that the
final wrapper wrote the tail, not that the final wrapper's own state selected
the ring consumer.  This is a final-client `bound != consumed` defect, not a
platform loss and not a failure of the short human stimulus.

## Claim boundary

Block B remains hardware-accepted.  Block A is **not** hardware-accepted, and
the v1.5 fast-typing Known Issue remains open.  The one observed sequence did
produce the correct visible string, but that cannot support a general
losslessness claim while two readers race at the hardware queue.

No repair, product link, medium or further device contact is authorized by
this result.  The successor question is narrow: make the delivered `read-line`
state select the private ring route, then require a permanent final-world
consumer gate that proves both arm and actual consumption by that exact
client.

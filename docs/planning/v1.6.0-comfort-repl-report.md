## 1. Behavior

The Comfort REPL adds one input layer and no second evaluator. Balanced input
is wrapped in one `(progn ...)`, passed to `read-from-string`, then handed to
the existing public `lcc-run` seam. It does not call a private compiler or
install path.

The shipped host-qualified behavior is:

- Return continues input while parenthesis depth is positive;
- indentation is two spaces per open level, capped at 20 spaces;
- a close parenthesis that crosses depth zero is sticky and is rejected before
  any form is evaluated;
- parentheses in strings and after a semicolon comment do not affect depth;
- Cursor Up/Down navigate a ten-line heap history;
- cursor motion and insertion reuse item 1's mutable line editor;
- each physical line retains the 250-character editor limit, while the
  aggregate form is heap-backed and may exceed the native 192-byte buffer;
- an empty balanced line returns to the native REPL.

The parenthesis scanner now has one source, `lib/sexp-depth.lisp`, shared by
the IDE syntax library and Comfort. The accepted base `read-line` signature is
still `(read-line) -> string`. Up/Down are generated from the common keymap;
without Comfort's appended history state they are harmless no-ops.

## Hardware contact — semantic pass, input-fidelity First Red

The owner-authorized same-world contact completed every functional row. The
Comfort shelf loaded, balanced and multiline evaluation worked, cursor-left
insertion preserved the suffix, over-close was rejected before evaluation,
history and the shared parenthesis scanner behaved correctly, a 201-byte
aggregate crossed the native line ceiling, and an empty Comfort line returned
to a live native prompt. The final screen contained no VM or disk error.

That semantic pass is not hardware acceptance. The owner reported that typing
inside Comfort was consistently clunky compared with the native REPL and that
physical keys were frequently not registered and had to be repeated. Lost
ordinary input is a correctness failure, not a cosmetic latency note. D5 and
all further device rows therefore remain closed.

The desk attribution names the structural class without overclaiming its final
timing split:

- the MEGA65 typed-event queue holds five events and drops a sixth while full;
- the native REPL consumes an event into a stack object and writes its byte
  directly into a static C buffer;
- Comfort calls public `key-event`, which materializes three heap cells, then
  allocates one editor cell for a printable character and completes its Lisp
  edit/render path before polling the queue again;
- the current executable host lane counts 1,259/1,275/1,291 VM instructions
  between polls for three ordinary appended characters, 1,016 for Cursor Left
  and 1,271 for a middle insertion;
- four cells per printable cross the 192-cell nursery in at most 48 printable
  keys even before other Comfort allocation. The only standing whole-target
  collection authority is 88--89 frames.

Thus the product has a synchronous consumer whose service gaps can exceed the
finite producer queue. Periodic collection is the strongest pre-registered
gap term, but this contact did not instrument the exact current VM/render/GC
split and does not pretend to. The permanent gate gap is already decisive:
the cursor card proved at most one collection per key, but never related that
pause to the five-event queue and never asserted zero dropped physical input.

The repair is priced before another contact. A lossless design must either
capture events independently of Lisp edit/render/GC work, or remove allocation
from the event and edit hot path and prove a queue-service bound. Merely adding
`poll-key` coalescing is insufficient unless its own event materialization is
proved unable to collect before the hardware queue is drained.

# lisp65 2.5.5 — Faster typing in the IDE editor

**Status: release candidate, not published.** The 2.5.5 Final is built and sealed (see Build identity). The device session on a physical MEGA65 passed on 2026-10-07 (see "Device session on a physical MEGA65" and the [device report](../planning/release-2.5.5-device-report.md)). The Before-Ship record and publication are **PENDING**; nothing marked PENDING is claimed as verified. The published baseline is 2.5.4.

This release is one card: typing in the IDE editor is faster. In the emulator a plain insert costs 57 ms instead of 124 to 150 ms, Backspace 60 ms instead of 107 to 133 ms, and the cost no longer grows with the column or the line. The change is on the Lisp plane only (four levers in the IDE library); native `.text` is unchanged at 36,899 bytes, and edit persistence (2.5.4) and the key-binding seam `ide-bind-key` behave as before. Every typing time in this note is **an emulator measurement, not a device timing**. On the device the owner found typing in the editor strongly improved, with Backspace still slightly delayed; the device values are an impression, two held-key counts and two stopwatch times, and they are marked as such.

## Changed: typing in the IDE editor

A study of the 2.5.4 editor found that 73 % of one key was spent loading code objects: the VM has one 56-byte execution buffer, so every call, tail call and return reloads. A printable key walked 24 keymap entries and 23 routes, the render path made 35 calls for three screen cells, and the editor loop stored a copy of the buffer before every key, at a cost that grew with the column and the line.

Four levers in the IDE library remove most of that:

- **L1.** A printable key is the insert command before the keymap table is searched; the insert route is tried first.
- **L4.** The routes of Backspace, Return and the cursor keys follow directly after it.
- **L3.** One-instruction accessors are written out as `car`/`cdr` in 21 functions of the key path (72 call sites).
- **L2.** The editor loop stores the buffer once on entry instead of before every key. What is stored after each finished editing step (the edit-persistence publication of 2.5.4) is unchanged.

**Counted on the host** (the delivered IDE world, one insert at line length 20): 1,955 VM instructions, 359 code-object reads and 95 heap cells in 2.5.4; 921, 145 and 39 in 2.5.5. Per-key cells fall from 95 to 39. A new source gate, `c2-v255-editor-key-cost-check`, holds ceilings on what one editing key may cost on the host VM.

**Edit persistence still holds.** The exhaustive abort-point proof was repeated on the delivered 2.5.5 IDE image (15,081 B, 204 objects): an abort at every VM instruction boundary kept every finished step, in the `drain` shape at 74,442 points and in the `run` shape at 127,914 points, with 10,056 and 27,871 multi-buffer points, 0 violations. The proof tool of 2.5.4 was blind in the `run` shape (it took its reference texts from the world it swept, and there from the per-key store that L2 removes); the 2.5.5 proof stands on its successor, which reads its references independently and requires the control without the publication to fail in both shapes (it does: 29,812 of 36,037 and 74,548 of 80,800 points). As in 2.5.4 the host proof covers aborts at VM instruction boundaries; aborts inside native primitives, during garbage collection or at out-of-memory are not covered by it. A direct `m65d-save` call is still not protected; only the IDE path is.

## Measured typing cost (emulator)

**This is an emulator measurement, not a device timing.** Emulator with a cycle counter at 40.5 MHz; the 2.5.4 Final and the 2.5.5 Seed medium (byte-identical to the Final medium) were measured on the same day, seven samples per point; the values are medians of keys on which no garbage collection fell (`build/card-255-typing-measure-r1`).

| Point | 2.5.4 | 2.5.5 | Ratio |
|---|---|---|---|
| Insert, column 1 | 124.2 ms | 57.3 ms | 0.461 |
| Insert, column 20 | 137.1 ms | 57.3 ms | 0.418 |
| Insert, column 39 | 150.0 ms | 57.3 ms | 0.382 |
| Insert, line 20 | 153.5 ms | 57.1 ms | 0.372 |
| Backspace, column 20 | 119.7 ms | 60.4 ms | 0.505 |
| Return, 30 characters | 462.9 ms | 416.3 ms | 0.899 |
| Burst of 8 keys | 687 ms | 244 ms | 0.355 |
| REPL, key to visible glyph | 14.0 ms | 14.0 ms | 1.000 |

Typing 60 single characters triggers 5 garbage collections instead of 9; with them the average is 67 ms per key instead of 152 ms. Every pass rule set before the measurement holds (insert at most 0.60 and Backspace at most 0.65 of the 2.5.4 control, Return not slower, growth with column and line at most 5 %, REPL within 1 %); the largest deviation from the prediction model is 2.3 %.

**What stays slow or unchanged:**

- **A garbage collection still costs about 120 ms**, in both versions. That is now about twice the cost of a key, so the pause is more noticeable relative to typing; it falls on about every twelfth key instead of every sixth or seventh.
- **The first key after entering the editor costs about 90 ms more**, in both versions.
- **Return is hardly faster:** 416 ms on a 30-character line (2.5.4: 463 ms). The repaint after Return is a later card.
- **On the device Backspace is still slightly delayed**, more so when the key is held (owner, 2026-10-07).
- **Type-ahead typed while the editor is still opening is lost** (unchanged since before 2.5.3; wait for the editor).
- **`(m65d-remount)` takes very long** on a well-filled disk (package unchanged).
- **Recalling a very long history entry with the prompt at the bottom of the screen draws it over the rows above** (display only; unchanged).
- **The `$D703` (DMA format) check has not been done on hardware.**

## Correction of a published 2.5.4 statement

The 2.5.4 release note and the 2.5.4 Before-Ship record said that the REPL inserts a character in 4.17 ms and that the editor is "about 30 times slower per key than the REPL"; the project status and the known issues carried the same figures. That comparison was wrong. 4.17 ms is the time from the consumed key to the next input poll; **the REPL glyph is visible 14.0 ms after the key is consumed**. For the same visible effect the 2.5.4 editor (124 to 150 ms) was **about 10 times slower than the REPL, not 30 times**. The editor figures of 2.5.4 stand. In 2.5.5 the editor is about 4 times slower than the REPL (57 ms against 14 ms). The text of the published v2.5.4 GitHub release is not edited; the 2.5.4 note in this repository carries a dated correction line, and the status documents are corrected in place.

## Residue zeroing on the medium

SHELF.BIN is two sectors shorter than in 2.5.4. The unchanged packer keeps the first sectors of a file's chain, marks the rest free and does not clear it, so 729 bytes of the 2.5.4 medium would have stayed in two freed sectors and behind the end of data in the new last sector. An explicit, asserted media step sets them to zero (506 of them were non-zero); no reader reaches these bytes, and the step is recorded in `residue-zeroing.json`. After it every sector the block map marks free is zero. The rule can be read from the medium alone and the public media reproduction needs no byte of the 2.5.4 medium for it.

One other file keeps old slack and is not touched by that step, because its sector count did not change: the cold stager `AUTOBOOT.C65` is six bytes shorter than in 2.5.4 and its last sector keeps the six bytes behind the new end of data. They equal the file's own last six bytes; no reader reaches them. Five files keep the non-zero slack they have had since earlier releases (SESSION.BIN, REGION1.BIN, PROFILE, INIT.L65, L65INDEX).

## Garbage-collection stress session

Forced collection at every allocation of each measured transition, in the emulator, on the Seed medium (`build/card-255-gc-r1`, baseline: the 2.5.4 session on the sealed 2.5.4 Final).

- Six of eight scenarios pass. Collections, allocations per transition and both peaks are equal to 2.5.4 in every scenario; the highest peak leaves 43 of 1,070 cells, as in 2.5.4. No out-of-memory.
- `history10` and `history-home-delete-refill250` stall as in 2.5.4, on the same display defect (a recalled 250-character entry drawn over the rows above), with the same figures.
- **By the committed rules the status of the gate is FAIL**, as in 2.5.4, because the two history scenarios do not complete. The gate is not reworded into a pass. There is no regression against 2.5.4. **The owner accepted the gate recorded as it is (formally FAIL, figures identical to 2.5.4) on 2026-10-07 and approved publication of 2.5.5 with it.**
- **Observation, a coincidence of driver and emulator, not a product stall:** the first attempt of the scenario `pending32` on the Seed medium ended in a breakpoint timeout at collection 471; the 470 collections before it equal the 2.5.4 sequence figure by figure. The scenario was then repeated in seven fresh boots, five on the sealed 2.5.5 Final and two on the sealed 2.5.4 Final. **It happened once and was not reproduced in seven runs:** all seven pass with identical figures (553 collections, peak 1,015 live cells and 4,889 arena bytes). The records of the failed attempt show that the forced allocation did call the collector, and that the frame interrupt was taken on the instruction boundary of the driver's breakpoint; the emulator then held the CPU inside the interrupt handler while the driver waited for the next address of the collector. It is the only such stop among 50,320 breakpoint stops in all GC session logs. The mechanism is inferred from those records; it was not provoked deliberately (`build/card-255-gc-pending32-r1`).
- All eight scenarios drive the REPL line editor. **No scenario covers the IDE editor under forced collection**, so the lower per-key allocation of 2.5.5 does not show in this session.

## Device session on a physical MEGA65

**Passed on 2026-10-07** as a manual owner session, as for 2.5.4: the owner typed and judged every row at the physical keyboard, so there is no tool-clock boot time and there are no automated device rows. The complete record is the [device report](../planning/release-2.5.5-device-report.md).

- Media: `D255.D81` (the Final medium, SHA-256 `4f0b76ad395ed861da104960859b8d9416750a00684dd4826a1193b14245523b`) and the user disk `D255U.D81` were uploaded as new files and read back byte-identical. After the session and a power cycle the product medium is unchanged.
- Boot by stopwatch: unchanged, 20 s to `Initializing`, then 22 s to `L65>`.
- **Typing in the IDE editor, in the owner's words: "Stark verbessert, Backspace immer noch leicht verzögert, stärker wenn Taste gehalten wird"** (strongly improved; Backspace still slightly delayed, more so when the key is held).
- Held key, counted by the owner on the 80-column screen: 227 characters in 10 s in the editor on an empty line and 202 at the `L65>` prompt, both about 20 to 23 characters per second. The reviewer reads this as follows: the REPL needs 14 ms per key in the emulator, so its count is limited by the keyboard repeat rate, and the editor now reaches the same ceiling. The repeat rate itself was not measured, and no 2.5.4 device count exists; in the emulator a burst costs 30 to 35 ms per key in 2.5.5 and 73 to 86 ms in 2.5.4.
- Two buffers with the **physical RUN/STOP key**: edits in both, switches by hand with `C-x C-p` and `C-x C-n`, RUN/STOP at idle; after re-entry both buffers were complete.
- Saving two buffers: both `save-buffer-to` calls returned `T`, and the host readback after the power cycle shows the two files exactly as expected. The 20x40 save took **4 s by the owner's stopwatch** (2.5.4: 5 s); the file is byte-identical to its source. The Freezer mount of the user disk gave no problem; the allocation map of the user disk is valid.
- Side finding of the owner, not a 2.5.5 matter: Return at the empty `L65>` prompt leaves Comfort for the native prompt. That is the documented behaviour since 2.5.0; the owner finds it surprising, and a small card is proposed in the register.
- Not done on the device: the keymap seam (unchanged against 2.5.4; the emulator rows are identical), the long checklist rows, the `$D703` check, held-key counts at column 35 and at line 20.

## Known issues

New or changed in this note:

- **Typing in the IDE editor is still about 4 times slower than at the REPL** (emulator: 57 ms against 14 ms per key), and a garbage collection of about 120 ms falls on about every twelfth key. On the device Backspace is still slightly delayed, more so when the key is held.
- **Return in the editor takes about 0.4 s** on a 30-character line (emulator).
- **The garbage-collection stress gate is recorded as FAIL**, as in 2.5.4 (two history scenarios stall on a display defect), and one `pending32` attempt timed out once: a coincidence of driver and emulator, not reproduced in seven repeats.

Carried over from 2.5.4 and unchanged: type-ahead typed while the editor opens is lost; `(m65d-remount)` is slow; the overdrawn recall of very long history entries at the bottom of the screen; 3 heap cells and 88 arena bytes less than 2.5.3; the `$D703` check not done on hardware; a direct `m65d-save` call is not protected by edit persistence and does not refuse a save during a source load; bounded result output is a Comfort-prompt guard only; the black screen once after a Freezer disk swap (cause unknown); a heap filled by data the program still holds cannot be released from the keyboard; a lambda stored in a top-level form is refused with `*** VM: BAD BYTECODE`; string literals over 255 bytes fail to compile; physical `C-x C-c` is unavailable (use `C-x q`); disks with REL files, GEOS files or a 1581 boot sector are refused for writing; no reclaim of leaked blocks; the Comfort limits (32 pending lines, 640 bytes, 250-character line, ten history entries of at most 250 bytes).

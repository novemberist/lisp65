# lisp65 2.5.4 — Edit persistence, IDE key bindings, faster IDE save

**Status: release candidate, not published.** The 2.5.4 Final is built and sealed (see Build identity). The device session on a physical MEGA65 passed on 2026-10-05 (see "Device session on a physical MEGA65" and the [device report](../planning/release-2.5.4-device-report.md)). The Before-Ship record and publication are **PENDING**; nothing marked PENDING is claimed as verified. The published baseline remains 2.5.3.

This release keeps finished editing steps when an IDE edit is interrupted, adds a small key-binding seam for packages, makes the IDE save build its source string through a cheaper primitive, fixes `(funcall (lambda ...) args)` in compiled forms, lets `mapcan` take more than 12 results, makes the compiler refuse `eq`, `eql` and the bit operations with the wrong number of arguments, and corrects three loadable packages. Native `.text` is unchanged at 36,899 bytes. Evidence is host-side (source suites, gates and an exhaustive abort-point proof of the edit-persistence mechanism on the delivered IDE image) plus emulator rows on the Seed medium; that medium (D81 and ELF) is byte-identical to the Final medium, so the rows ran on the identical medium (see "Emulator rows on the Seed medium"). The physical MEGA65 results are in "Device session on a physical MEGA65"; that session was a manual owner session and covered fewer rows than the emulator.

## Changed: edit persistence in the IDE (E3)

An IDE edit that is interrupted, for example by RUN/STOP while typing, no longer loses editing steps that had already finished. Each finished editing step is stored before the next key is polled, without allocating; Return copies the typing list instead of consuming it; and a `C-x` prefix left pending by RUN/STOP is reset, so it no longer captures the first key of the next session. The contract is: every key whose editing step completed survives RUN/STOP; the key being processed when the abort arrives may be lost.

- **Only the IDE path is protected.** A direct `m65d-save` call is **not** protected by the edit-persistence mechanism; it stays outside the IDE and has no such guard.
- **Host proof.** On the delivered IDE image (15,223 B, 204 objects) an abort at every VM instruction boundary kept every finished step: 381,706 points and 52,091 multi-buffer points, 0 violations. Both controls fail as required (without the product seams 170,774 violations, without the Return copy 7,262).
- **What the host proof does not cover:** aborts inside native primitives, during garbage collection or at out-of-memory. These are the subject of emulator rows and of one physical RUN/STOP row on the device. Emulator rows on the Seed medium: all 20 abort points and both pending-`C-x` rows read `OK`. The RUN/STOP stand-in in the emulator is a monitor write to the break flag and is accepted for the emulator only. On the device (2026-10-05) the owner waited for the editor, typed `abcdefgh`, pressed the physical RUN/STOP key and re-entered the editor: the text was complete and identical to what had been visible before the stop. Keys appear immediately on the device, so a stop in the middle of a key burst cannot be produced by hand; that case is covered by the emulator rows only.

## Added: IDE key bindings for packages (`ide-bind-key`)

`(ide-bind-key KEY FUNCTION)` binds `C-x` followed by the printable character with code `KEY` to `FUNCTION` (normally a quoted symbol). The function is called with the current buffer and returns a new buffer, a message string, or `nil` (no change). Only keys the generated keymap leaves unbound reach the seam, so **built-in keys cannot be overridden**; a later binding of the same key shadows an earlier one. An unbound `C-x` plus a printable key now shows `unknown command` (before, it was silently ignored). The seam is for loaded packages; there is no launcher-name variant in this release. The emulator rows of the seam on the Seed medium passed (unbound key shows `unknown command`, a bound function replaces the buffer, a message result, a `nil` result, a control key after `C-x` cancels the prefix, a built-in key is not overridden, the registry value). On the device `C-x f` unbound showed `UNKNOWN COMMAND` in the status row, and after `(ide-bind-key 102 'seam-bang)` it inserted `!`.

## Changed: IDE save

Cause of the slow save in 2.5.3: the packed source join wrote one byte per call through a Buffer primitive, and each such call runs a full runtime-overlay load (about 47 ms per call on the device, derived from the 2.5.3 device-session tool clock; a 1,849-byte save took 92 s). In 2.5.4 the save string is built through the resident staging primitive and frozen in one step. The disk contract is unchanged: an out-of-memory at the allocation still happens before any M65D write.

- **Save during a source load.** Every IDE save is refused while a source load is active (`save refused while a file loads`), because a save from a top-level form of the file being loaded would replace the chain the loader is still reading. A direct `m65d-save` outside the IDE is not guarded.
- **Measured save time on the device:** `(save-buffer-to "out20x40" "big")` of the 20x40 buffer (739 bytes) took **5 s by the owner's stopwatch**; the 2.5.3 device reference for the same save is 37.7 s (driver clock). The file was byte-identical to its source on the host readback after a power cycle. Larger saves (50x40, 100x20), the physical `C-x C-s` path and `eval-buffer` were not measured on the device. The emulator rows for the 20x40 and 50x40 saves and for the refusal during a load passed. The remount and the disk-owner map are unchanged (the separate remount speed-up is deferred).

## Fixed: compiler (LCC) and `mapcan`

- `(funcall (lambda (p ...) body) a ...)` is compiled as the direct form `((lambda (p ...) body) a ...)` instead of producing a transient code image. A lambda that is stored in a top-level form (for example `(setq f (lambda ...))`) stays refused with `*** VM: BAD BYTECODE`. The emulator rows on the Seed medium passed for the compiled closure form, for the stored lambda that stays refused and for the nesting ladder with closures.
- `eq`, `eql`, `logand`, `logior`, `logxor` and `ash` refuse any argument count other than two on the product compiler path (the screen shows `*** COMPILE FAILED%LCC-ERROR-INVALID-PARAMETER-LIST`); surplus arguments are no longer dropped without being evaluated.
- `mapcan` works with more than 12 results: results are folded two at a time from the right, the last result stays uncopied, as in `(apply append ...)`.
- The compile-time nesting depth of `setq`/`let` forms is not below 2.5.3 on any of the 35 shapes of the `lcc-nesting-ladder-check` gate (host).

## Fixed: loadable packages

- **RP1, bounded Comfort result output.** At the Comfort prompt a result that is deeper than 8 levels, larger than 1,100 conses, or circular is refused with `*** result too deep, too large or circular` instead of being printed. Explicit `prin1`/`print` calls and the native `LISP65>` prompt do not use this guard and stay unbounded (a cyclic list printed there can still run indefinitely).
- **LIB1.** `defstruct` rejects a structure whose generated names collide (for example a slot named `p` with the structure predicate).
- **HIST1.** A recalled multi-line history entry that contains a comment is submitted at once instead of leaving Comfort waiting for more input.

## Emulator rows on the Seed medium

That D81 and ELF are byte-identical to the Final medium and ELF, so these are rows on the identical medium. All figures are emulator observations, not device timings.

- **No product failure.** Of the new 2.5.4 rows 31 pass automatically and 30 capture-then-review rows were accepted by the reviewer; no row fails. Rows with a device-dependent expectation are captured and reviewed; none passes automatically.

## Device session on a physical MEGA65

**Passed on 2026-10-05** on the Final medium (`D254.D81`, SHA-256 `250fdc763ae9e5b04cf149a6f2a7a3aa9fb293ff8da58e9a703e0c601efaef5d`), as a manual owner session at the physical keyboard; see the [device report](../planning/release-2.5.4-device-report.md). There was no device driver in this session, so there is no tool-clock boot time and there are no automated device rows.

- Upload: `D254.D81` and the user disk `D254U.D81` were read back byte-identical after the upload; after the session and a power cycle the product disk was unchanged.
- Boot by stopwatch: 20 s to `Initializing`, then 22 s to `L65>` (42 s).
- Physical RUN/STOP at the prompt: `(while t nil)` aborted with `*** STOPPED (RUN/STOP)`, the prompt returned and `(+ 4 5)` gave 9.
- Edit persistence with the physical key: text visible before RUN/STOP was complete after re-entry (see "Changed: edit persistence in the IDE").
- Keymap seam: `C-x f` unbound showed `UNKNOWN COMMAND`; after `ide-bind-key` it inserted `!`.
- IDE save of the 20x40 buffer with `save-buffer-to`: 5 s by stopwatch (2.5.3: 37.7 s), file byte-identical on host readback, disk allocation map valid. The Freezer disk swap showed no problem.

Findings of the session; none is a 2.5.4 regression by current evidence (for typing see the emulator comparison below). The owner released the three findings as known limits for 2.5.4 on 2026-10-05; faster editor typing is the first card of the next cycle.

- **Type-ahead while the editor opens is lost.** Keys typed immediately after Return on `(ide "name")`, before the editor is on screen, do not arrive (of `abcdefgh` only `fgh` appeared). The editor entry resets the input counters; that code predates 2.5.3.
- **Typing in the IDE editor is clearly slower than at the REPL.** Keys are not lost; they appear late when typing fast. The owner could not compare with the 2.5.3 editor on the device and notes that the editor was never actively optimised. Emulator comparison of the editor (cycle counter, 40.5 MHz, Seed medium, 2.5.3 against 2.5.4): insert 122.3 against 124.2 ms per key at line length 1 and 148.0 against 150.0 ms at length 39, Backspace 104.9–130.4 against 106.7–132.5 ms, Return after 30 characters 460.6 against 462.9 ms; the ratio is about 1.013–1.017, a constant +73k cycles (1.8 ms) per key. A REPL insert costs 4.17 ms in both versions. In both versions a collection of 116–123 ms falls on about one in five or six editor keys, and a burst of keys is drawn once at its end. So 2.5.4 does not make the editor meaningfully slower; the editor is about 30 times slower per key than the REPL in both versions.
- **`(m65d-remount)` takes very long on the device** (no time recorded). The owner believes this is unchanged; the M65D image is byte-identical to 2.5.3.

Not done on the device: the additional REPL rows, large saves (50x40, 100x20), the out-of-memory rows and the `$D703` check, which stays open on hardware.

## Garbage-collection stress session on the Final

Emulator session on the sealed 2.5.4 Final with a collection forced at every allocation of each measured transition (`build/card-254-gc-r2/summary.json`). **By the committed rules the status of the gate is FAIL**, and it is recorded as such:

- Six of eight scenarios pass with no out-of-memory: `return250`, `pending32`, `join640`, `reopen`, `defmacro-gc` and `reopen-home-delete-refill250` (on a rerun). `return250` and `reopen-home-delete-refill250` completed for the first time; 2.5.3 never got through them.
- `history10` and `history-home-delete-refill250` **stall on a display defect that is identical in the 2.5.3 records**: with the prompt at the bottom of the screen a recalled 250-character history entry is drawn over the three rows above without scrolling, and stale cells remain. Cursor keys, Delete and Return work and the value is right. Not covered therefore: Return of a recalled 250-character entry and delete/refill inside one under forced collection.
- **Memory cost against the 2.5.3 Final: a constant +3 live cells and +88 arena bytes at every collection** (reasoned cause: the bounded result print, whose two functions and message string exist only in 2.5.4). Headroom at the highest forced peak is 43 of 1,070 cells (2.5.3: 46). The comparison rule requires peaks not above 2.5.3, so both comparisons fail.

**The owner accepted this memory cost on 2026-10-06 and approved publication of 2.5.4 with the gate recorded as it is (formally FAIL).** The gate is not reworded into a pass.

## Known issues

New or changed in this note:

- **Type-ahead while the IDE editor opens is lost.** Wait until the editor is on screen before typing. Not new in 2.5.4; found in the 2.5.4 device session.
- **Typing in the IDE editor is slower than at the REPL prompt.** Keys are not lost but appear late when typing fast (device observation). An editor latency card is planned for the next cycle.
- **`(m65d-remount)` is slow on the device.** Unchanged code; a speed-up is a candidate for a later release.
- **`$D703` (DMA format) is unverified on hardware.** The emulator probe survived; the device check was not done.
- **A recalled very long history entry can be drawn over the rows above it.** With the prompt at the bottom of the screen, recalling a 250-character entry draws it over the three rows above without scrolling and leaves stale cells. Display only: editing and Return work and the value is right. Not new in 2.5.4 (identical in the 2.5.3 records).
- **Three heap cells and 88 arena bytes less than in 2.5.3** at every point of a session (see "Garbage-collection stress session on the Final").

- **A direct `m65d-save` call is not protected by the edit-persistence mechanism.** Only the IDE path is. A direct `m65d-save` also does not refuse a save during a source load (only the IDE saves do).
- **Edit persistence is proven on the host only for aborts at VM instruction boundaries.** Aborts inside native primitives, during garbage collection or at out-of-memory are not covered by the host proof; see the rows above.
- **Bounded result output is a Comfort-prompt guard only.** Explicit `prin1`/`print` and the native `LISP65>` prompt can still run indefinitely on a cyclic list.

Carried over from 2.5.3 and unchanged unless listed above: the black screen once after a Freezer disk swap (cause unknown); a heap filled by data the program still holds cannot be released from the keyboard; a lambda stored in a top-level form is refused with `*** VM: BAD BYTECODE`; individual string literals over 255 bytes fail to compile; physical `C-x C-c` is unavailable (use `C-x q`); disks with REL files, GEOS files or a 1581 boot sector are refused for writing; no reclaim of leaked blocks; the Comfort limits (32 pending lines, 640 bytes, 250-character line, ten history entries of at most 250 bytes). The 2.5.3 note's "A physical `C-x C-s` on a 50x40 buffer can take several minutes" is the case save fix A addresses; on the device the 20x40 save now takes 5 s, and the 50x40 save was not repeated there.

Deferred beyond 2.5.4: the second save fix (remount owner map in the stage), the private-inline `%m65d-mask` change, native items, block reclaim.

Fixed since 2.5.3 and therefore no longer listed: `mapcan` with more than 12 results, `(funcall (lambda ...) args)` of a closure form, surplus arguments to `eq`/`eql`/bit operations, `defstruct` name collisions, the Comfort wait after a recalled history entry with a comment, and (Comfort prompt only) the hang when printing a cyclic result.

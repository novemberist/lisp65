# lisp65 2.5.3 — Larger IDE saves, safer disks, LCC fixes

**Status: release candidate, not published.** The 2.5.3 Final is built and sealed (see Build identity). The device session on a physical MEGA65 passed on 2026-10-03 (see "Device session on a physical MEGA65" and the [device report](../planning/release-2.5.3-device-report.md)). The Before-Ship record and publication are **PENDING**; nothing marked PENDING is claimed as verified. The published baseline remains 2.5.2.

This release fixes the IDE save/eval memory defect, the out-of-memory hang (after `*** VM: OUT OF MEMORY` the prompt returns) and the silent partial `eval-buffer`, repairs two IDE editing defects, makes the compiler refuse malformed builtin calls and assign every pair of a multi-pair `setq`, and tightens disk handling: writes are enabled only after a check of the whole disk, loading a file no longer removes anything, and a full 144-file directory can be mounted again. Evidence is host-side (source suites and gates) plus emulator rows on the Seed r8 medium; that medium (D81 and ELF) is byte-identical to the Final r8 medium, so the rows ran on the identical medium (see "Emulator rows on the Seed r8 medium"). The physical MEGA65 session passed; its results, and one display failure that is not explained, are in "Device session on a physical MEGA65".

## Fixed: IDE save and eval-buffer with larger buffers

`C-x C-s`, `save-buffer-to` and `eval-buffer` no longer build a character list for the whole buffer. They join the lines into one packed buffer and hand that buffer to the disk writer or reader. The additional temporary heap for a 50-line, 40-character buffer fell from 2,207 to 212 cells for saving and from 2,206 to 181 cells for `eval-buffer` (host measurement against the 2.5.2 code).

Limits in host fixtures with the same budget as the 2.5.2 notes (588 additional heap cells, 8,049 additional arena bytes), last successful buffer sizes:

| Line width | Without edit cache | With edit cache |
|---:|---:|---:|
| 20 | 196 lines | 119 lines |
| 40 | 99 lines | 98 lines |
| 70 | 57 lines | 56 lines |

**These are host test results, not guaranteed limits.** Other live data, many short or empty lines (they can exhaust the cell heap first), and the program being evaluated can require more memory. Saves are also limited to 8,192 bytes by M65D.

Emulator rows on the Seed r8 medium (the 2.5.2 Final ran out of memory at 50 lines of 40 characters): saving a 20x40 and a 50x40 buffer passed with a byte-identical reload on the host (739 and 1,849 bytes, command path and editor keys); a 100x20 save (1,899 bytes) passed in a fresh session; `eval-buffer` of 5 and 50 forms passed. A 100x40 save ran out of memory (the message appeared after about 190 s) before any disk write; the prompt returned, `(+ 1 2)` gave 3, the IDE buffers could be dropped, the source file stayed intact and no output file appeared. Device (physical MEGA65, tool clock, upper bounds, not guarantees): `save-buffer-to` of a 20x40 buffer 37.7 s and of a 50x40 buffer 92.1 s, the editor-key save 37.2 s and 91.7 s, both reloaded byte-identically on the host. **A physical `C-x C-s` on a 50x40 buffer took several minutes** (it showed SAVED and wrote the file correctly); the cause of the difference from the driver's editor-key save is not established.

## Fixed: the prompt returns after out of memory

In 2.5.2 and in the earlier, unshipped r7 candidate, `*** VM: OUT OF MEMORY` could leave the prompt dead: the message repeated and keys were not accepted. The cause was a sticky out-of-memory flag in the C runtime that the error landing never cleared; 2.5.3 clears it where the REPL regains control (a one-line change in `repl()`; host gate `repl-oom-recovery-check`). Emulator rows on the Seed r8 medium:

- Plain REPL, runaway garbage in a `let`-local: `*** VM: OUT OF MEMORY` appears once, the prompt returns, `(+ 1 2)` gives 3 and a fresh `(length (list 1 2 3))` gives 3.
- Failed IDE save (100x40): message, prompt back, 3, IDE buffers dropped, 7, 3.
- A 249-character line typed with the IDE, M65D and four IDE buffers loaded: memory ran out while typing (around key 214, after 46 to 52 s of typing); a new `L65>` prompt appeared and the remaining six keys and the closing quote landed on it as a continuation line (an open string, not a dead prompt); after the closing quote the value was printed, `(+ 1 2)` gave 3 and `(length ide-buffers)` gave 4. In 2.5.2 and r7 this prompt was dead.

**Limit: a heap filled by data the program still holds cannot be released from the keyboard.** After filling the heap with a global list, the prompt returned and `(+ 1 2)` still gave 3, but every attempt to drop the list (`(setq l nil)`, `(set-symbol-value (quote l) nil)`) ran out of memory while it was being typed, because typing itself needs memory. After the first failure the Comfort prompt `L65>` was replaced by the native `LISP65>`; there the same keys kept failing with the message, nothing was evaluated, the prompt always returned (no endless message loop), and the list stayed live. A reset is required in that case. Runaway garbage, `let`-locals and failed IDE saves recover as above. Device: in the optional last row the heap was filled with a global list; the message appeared and the prompt returned; the session was then ended and the machine reset as required (the freeing attempt was not repeated on the device).

## Fixed: eval-buffer could stop early without an error

`eval-buffer` kept its joined source string unrooted; a garbage collection during compilation could reclaim it and stop evaluation after the first forms with no message. The source is now kept alive by the reader loop (`%ide-eval-source`). Host evidence: 2,365 allocation-point root markers over the tested buffers found the source rooted, and all 55 forms of the test buffers ran. In the emulator, `eval-buffer` of 5 and 50 forms returned all forms under natural collection. On the r7 medium of the unshipped candidate (not repeated on r8), `eval-buffer` of 5 forms (1,688 allocations) and of 50 forms (14,205 allocations) was run with a collection forced at every allocation and returned all forms (`(5 DONE NIL)`, `(50 DONE NIL)`; peak live 638 and 728 cells, `mem_oom` never set).

## Fixed: a temporary macro name could be collected

The internal macro-install service (`%set-macro`) now roots its temporary name while it allocates. The finding was never demonstrated for ordinary `defmacro` with an interned name. In the emulator on the Seed r8 medium, `defmacro` rows passed, a forced-collection run of the macro install passed (267 forced collections, peak 568 live cells, no exhaustion), and the expansion `(my-id 7)` under a collection at every allocation returned 7 (431 collections, peak 539 cells). The linked growth exceeded the earlier planned cap of +256 B; the owner raised the cap to +352 B (2026-10-01) and then slightly further to **+368 B** (2026-10-02, "raise the cap slightly"); the build is within the +368 B cap.

## Fixed: IDE buffer switch and stale marks

- With only one buffer open, switching buffers no longer reactivates an older state of that buffer; text typed just before the switch is kept. With several buffers, switching behaves as before.
- **Every text edit now clears the mark.** Previously a mark kept across edits could point past the end of the text and a later `C-x C-x` or typing could misbehave. After an edit, set the mark again with `C-x Space`.

Host evidence: 169 IDE state cases, 53 reviewer probes and 90 latency scenarios without cost regression (no timing in milliseconds). Emulator rows on the Seed r8 medium for the buffer switch (also with two buffers) and the mark passed at function level; the editor-key path passed for the buffer switch, for the switch between two buffers (a, b, a, b, each buffer keeping its text) and for evaluating a dirty buffer. The editor-key row for the mark (a mark set before an edit is cleared by it) was run only on the r7 medium of the unshipped candidate. Device (2026-10-03): the buffer-switch rows with one and with two buffers, the dirty-buffer `eval-buffer` row and the mark-cleared-by-edit row passed on the physical MEGA65, and the owner confirmed physical `C-x q`.

## Fixed: compiler (LCC)

- **Multi-pair `setq`:** `(setq a 1 b 2)` assigns every pair in order and yields the last value, in statement and value position. The first fix left one surplus value per extra pair on the VM stack; that was found in review and fixed by dropping the intermediate values, matching the C compiler. Host probes: `(+ 100 (setq a 1 b 2))` = 102, globals and three pairs, and loops of 600 and 2,000 iterations keep a bounded stack depth. Emulator rows on the Seed r8 medium passed (including `102`, `(100 2 7)` and loops of 1,198 and 3,998; the multi-pair `setq`, odd-`setq` and probe rows passed on r8). An odd number of arguments (`(setq a)`) is refused as an invalid parameter list.
- **Builtin argument counts, also on the product compiler path:** the product compiler takes its builtin dispatch from the Dialect V2 profile (`lib/dialect-v2/lcc-profile.lisp`), which had shadowed the first arity guard; it now carries its own. `car`, `cdr`, `consp`, `not` and `null` require exactly one argument; `cons` and `mod` exactly two. (`remainder` is not a Dialect V2 source operation and is not checked.) In a compiled form such as a `defun` body, other counts are refused at compile time instead of being silently accepted with surplus arguments dropped. **Exact screen text (emulator, Seed r8 medium): `*** COMPILE FAILED%LCC-ERROR-INVALID-PARAMETER-LIST`**: the internal name follows the stable text directly and does not say which builtin or how many arguments were expected. The same call typed as a top-level form reports `*** WRONG ARGUMENT COUNT`. The prompt recovers in both cases.
- **`nth`:** `nth` now checks the whole list first. A dotted tail anywhere in the list gives a type error, even when the requested element lies before it, and a non-negative index past a proper list still returns `nil`. The emulator row (seven steps) passed.

- **Nesting depth:** the compile-time nesting depth of `setq` and `let` forms equals 2.5.2 (new gate `lcc-nesting-ladder-check`, 35 shapes). On the Seed r8 medium the calibrated ladder passed 12/12: the deepest accepted form gives its value and one level deeper gives `*** VM: STACK OVERFLOW` with the prompt returning (`let`+`setq` 8 ok / 9 overflow, `let`+`dotimes`+`setq` 6/7, `let` arithmetic 10/11, `let`+`dotimes` 7/8, `let`+`while`+`setq` 6/7, `defun`+`let`+`setq` 8/9). The reported 96-form `let`/`dotimes`/`setq` form compiles and runs (value 0).

`mapcan` with more than 12 input elements still fails; see Known issues.

## Changed: disk writes, load and remount

**Write enable (D2).** Writing is allowed only after a successful remount (the IDE remounts automatically when a save needs it), and only to the disk that remount checked. The remount reads the directory and every file chain into an ownership map and compares it with the block allocation map (BAM). It refuses a disk with a block owned by two files, a cycle in a chain, a link into track 40 or to a sector at or above 40, a block marked free that a file uses, or an allocated block that no file owns. Disks that pass are written as before.

**Refusal message and aborted saves (D4).** A refused disk reports status 13, shown in the IDE as `disk allocation inconsistent; disk not written`; nothing is written and the buffer and disk stay as they are. A save keeps its transaction open until it returns: after an abort (RUN/STOP, error, read abort) the next save returns status 8 without writing and requires a remount, which runs the check again. **There is no reclaim in this release.** Blocks leaked by an interrupted save are neither freed nor repaired, and a disk refused with status 13 stays read-only until it is repaired with an external 1581 tool (for example `c1541` `validate`) or its files are copied to a fresh disk. A reclaim is planned as a 2.5.4 card. The check costs about one sector read per file block at remount only; saves after a remount cost no more than before.

Host evidence: the M65D suite 48/48, IDE core suite 169/169, a 287-row cut-point matrix with 0 failures (all 33 states that leak blocks were detected, no clean disk was refused; clean controls include blank, 2, 9, 40 and 144 files and a 48-file, 1,584-block disk), D3/D5 cases 37/37. The new permanent gate `m65d-disk-integrity-check` is part of `check-source`. Emulator rows on prepared disk images (Seed r8 medium) passed for the write enable (status 8 after an aborted save simulated through the oracle marker, status 12 then 8 after a real swap to another disk identity), for D4 (status `(13 8 13)`, reads still work, the refused image stayed byte-identical) and for D5. A write-fault injection row (`ide-save-cow-controls`) was not run. Host readbacks on r8: the 20x40, 50x40 and 100x20 saves (739, 1,849 and 1,899 bytes) and the D3 file are byte-identical on reload, and a 144-file image keeps all files. Device (real disks, 2026-10-03): all 12 groups of the user-disk phase (remount, saves, D3, aborted-save and remount sequence), the swap refusal (status 12, then 8), the leaked-block disk (`(13 8 13)`, status 13, reads still work, a save refused with `disk allocation inconsistent`) and the 144-file disk (remount, replace of the first file, 144 files listed) passed; host readbacks showed the refused and untouched disks byte-identical and the 144-file disk with the first file replaced and 143 siblings intact.

**Lossless load (D3).** Loading a file into the IDE now keeps its exact bytes: trailing spaces, trailing empty lines and carriage returns are preserved, and only line feed separates lines. Load followed by save is byte-exact in all 37 host cases and in the emulator row (a 17-byte file with carriage returns and trailing spaces). Consequences:

- A carriage return stays in the line and is drawn as a **blank cell**. It occupies one column, the cursor can stand on it and Delete/Backspace removes it, but it is not visible. The reader treats it as whitespace, so `eval-buffer` and `compile-file-to-lib` accept CRLF files. A lone carriage return inside a `;` comment does not end the comment; comments end at line feed.
- A file ending in a line feed loads with a trailing empty line.
- **Files written by the pre-1.0 overwrite-in-place `save` into a preallocated slot now show their right-hand space padding** (a final line of spaces). The disk format has no marker for such slots, so they cannot be told from ordinary files. The Lisp reader ignores the padding; the next IDE save writes it back, so the file grows by the padding.

**Full directory (D5).** A completely full directory of 144 files now remounts, and replacing an existing file on it works (emulator row: 144 files, first file replaced, the others intact). A new name is still refused (status 5).

## Known issues

New in this note:

- **Black screen after a Freezer disk swap (observed once on the device, cause unknown).** After mounting a disk through the Freezer and returning with F3 the display went black and the Freezer hung; a power cycle was needed. No disk was damaged. It did not recur in three later swaps. Do not rely on a swap being safe for unsaved work; save and keep backups first.
- **A physical `C-x C-s` on a 50x40 buffer can take several minutes** (once, on the device; the file was written correctly). Wait for SAVED.
- **A heap filled by data the program still holds cannot be released from the keyboard.** If the heap is exhausted by something that stays reachable (for example a global list built in a loop), lisp65 prints `*** VM: OUT OF MEMORY` once and the prompt returns, and short forms such as `(+ 1 2)` still work. Typing the form that would free the data (`(setq l nil)`) runs out of memory while it is being typed, because typing itself needs memory; after the first failure the Comfort prompt `L65>` is replaced by the native `LISP65>`, the same keys keep failing with the message, nothing is evaluated and the data stays live. Reset (power cycle); unsaved buffers are lost. Runaway garbage in a `let`-local, a failed IDE save and typing with many IDE buffers recover (see "Fixed: the prompt returns after out of memory"). Observed in the emulator; on the device the message and the returning prompt were seen, and the freeing attempt was not repeated.
- **Closures capturing a `let` variable at the Comfort prompt.** `(funcall (lambda () ...))` with a lambda that captures a `let` variable, even `(funcall (lambda () (setq s i)))`, gives `*** VM: BAD BYTECODE`; the prompt returns. This is the known refusal of top-level anonymous `lambda` (see [Known Issues](../known-issues.md)) and is identical on 2.5.2 and on the unshipped r7 candidate (probes `bb-r8`, `bb-253`, `bb-252` in `build/card-253-rows-r8`).

Not a limitation of this release: a refusal because of code space or the 64 code images also prints `*** VM: OUT OF MEMORY`; the prompt returned there already in 2.5.2, and 2.5.3 only raises the size at which it happens.

Carried over, not fixed in 2.5.3:

- `mapcan` fails with more than 12 input elements (it exceeds the 12-argument call limit internally). Fix descoped.
- Individual string literals over **255 bytes** fail to compile with `*** VM: BAD BYTECODE`; the 640-byte Comfort source limit does not enlarge the literal format.
- Physical **C-x C-c** remains unavailable. Use **C-x q** (release Ctrl before q).
- M65D refuses to write to disks whose extra blocks are not reachable through file chains: **REL files, GEOS files, a 1581 boot sector** or other formats that reserve blocks outside file chains. Reading and loading are unaffected. Use a plain disk for work.
- Two disks with a byte-identical 16-byte name and 2-byte ID cannot be told apart. Swapping to an unchecked clone after the remount is not detected. A clone swapped during the remount itself is also not detected.
- A medium swap before the first write of a save reports status 12 (`medium changed during write; check both disks`) although nothing was written.
- **No reclaim of leaked blocks.** Interrupted saves can still leave allocated blocks with no owning file; the next remount refuses that disk (status 13). Host tests between completed logical-sector writes preserved the old or new file; this does not establish protection against interrupted physical writes or power loss.
- A disk chain changed between the loader's two read passes is not rejected (remaining-length check not included).
- Directory listing can return partial results after a read failure; RUN/STOP in the IDE can discard the most recent input batch; Comfort limits (32 pending lines, 640 bytes, 250-character line, ten history entries of at most 250 bytes), history recall with comments, cyclic printing, symbol round-trips, `defstruct` name clashes, top-level anonymous `lambda` (including closures over `let` variables, above), the 12-argument call limit, `require` inside temporary compiled forms and the other items under "Other known limitations" in the [2.5.2 notes](2.5.2.md) are unchanged.
